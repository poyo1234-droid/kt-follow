## 4. JANコード

### 検品出荷_撮影指示付.xlsm の商品マスタ参照（2026-09-11 調査）

- 参照は3か所。**すべて読み取りのみ。書き込みは無い**
  - `Shohin_Get_ByJan` … JANコード完全一致 limit 1 → 入荷/出荷/B品の各行へ自動補完
  - `Aimai_Brnd_Kintone` … ブランド品番／CS別品番／JAN の部分一致OR検索 limit 100
  - `GetCsListByJan` … JAN部分一致 → CS別品番→ブランド品番の辞書（撮影所在庫検索で使用）
- 接続は kintone REST API のみ。アプリID 51、トークン・IDは
  `納品書作成\config\kintone_config.xlsx` の C14／C15（パスは xlsm の「設定」シート A2）
- 商品単価は使っていないため、納品書VBAのような「上代が登録時のまま」の問題は起きない
- `Zaiko_Post`（旭川在庫管理69へのPOST）のトークンヘッダに商品マスタのトークンを併記。
  在庫アプリ側のルックアップ解決のためで、実質は読み取り権限
- Module1.bas の「ZOZO商品マスタ」「A商品マスタ」は Access（`ZOZO納品書＆JANコードラベル(親).mdb`）
  のテーブルで、kintoneの商品マスタではない。入荷JAN読取のC〜G列のVLOOKUP式はこのAccess由来
  シートを見ており、kintone経路と併存している
- 詳細は `商品マスタ参照箇所_20260910.md`

### 703件の根拠（Access由来 `マスタ\ZOZO商品マスタ.csv` × goods_cs 9/7、CS別品番で突合）

一致した345,675件の内訳:

| 状態 | 件数 |
|---|---|
| JANコードとバーコードが完全一致 | 342,407（99.06%） |
| goods_csが「/」区切りで複数。商品マスタが**最新側（末尾）**を持つ | 2,286 |
| goods_csが「/」区切りで複数。商品マスタが**旧側（先頭）**を持つ | **324** |
| 値が別物 | **379** |
| goods_cs側が空 | 279 |

- 「値が別物」379件は、商品マスタ側が `1121…` `1185…`（自社採番）、goods_cs側が
  `4571509…`（メーカーJAN）というパターン
- 実害が出る可能性があるのは 324 + 379 = **703件（全体の0.20%）**
- 引けなかったときは `MsgBox "JANコードが商品マスタに見つかりません"` で止まる作りなので、
  黙って壊れることはない。現場が「たまにスキャンで出てこない商品がある」と感じているかが
  実害の有無の手掛かりになる

### 担当者回答（2026-09-11）

- 基本はメーカー様支給のJANを商品マスタに登録。支給が無いものは自社採番
- goods_csのバーコードが「/」区切りのときは**後者が最新**
- ZOZO登録後のJAN変更は行ってきた（商品仕様変更時など）。
  通常は商品マスタ更新→ZOZOへ登録の順だが、担当者がZOZO管理画面から直接変更し、
  そのあと商品マスタの更新モレが発生したこともある

### 判断と代替案

- **「JAN変更時は商品マスタも必ず更新する」というルール運用はNG**（2026-09-11 ユーザー判断）。
  過去に実際に更新モレが発生しており、ルールを決め直しても再発を防げないため
- 「B案が実現できれば登録時のJANのままでOK」は**そのままでは成り立たない**。
  CS別品番はZOZO側の都合で変わる値なのでgoods_csから読めば済むが、
  **JANは現物に印字されている値**であり、現物が変われば商品マスタも変えないと引けない
- 代替案（B案と整合する方向）: 商品マスタを更新するのではなく、
  **JANで引けなかったときだけ goods_csアプリのバーコードで探し、商品展開ID経由で
  商品マスタへ読み替える二段検索**にする。CS品番で検討中の読み替えと同じ考え方で、
  商品マスタへの書き込みを増やさずに703件を救える
- これを採る場合、**検品出荷VBAは改修対象**になる（当初「改修不要」と見立てたが訂正）

- 社内メモの代替案（goods_csのバーコード経由で商品展開IDへ読み替える二段検索）は、
  採用すれば既存703件も救えるが、上記のとおり優先度は低い

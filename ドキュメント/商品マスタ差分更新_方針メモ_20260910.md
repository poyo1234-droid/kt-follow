# 商品マスタ差分更新 方針メモ（2026-09-10）

> **【白紙撤回 2026-09-10】この案（下記「検討した案」1〜7）は同日ユーザー判断で白紙に戻した。**
> 理由: 煩雑で間違いが起きそう。更新時に問題がありそう。
> 以下は検討の記録として残す。「確認済みの事実」は引き続き有効。
> 白紙後も維持する考え: 商品マスタのCS別品番は上書きしない／セール・フォローで同じ商品が2重に出力されるのはNG

背景: フォローリストの価格系3列（販売価格・価格タイプ・販売タイプ）の保持先の検討から、商品マスタの管理方針の議論に発展。
根拠資料: `goods_cs-2時点比較_20260910.md`（販売日は更新日にならない／商品展開IDはキーに使える）、`商品マスタ参照箇所_20260910.md`（商品マスタを使う仕組みの一覧）

## 前提（ユーザー方針）
- kintoneは開発最終段階。最優先は旧システム（Win10で稼働）から抜け出すこと
- 当面、kintoneのコード・参照先は現状のまま運用し、その後段階的に切り替える

## 検討した案（白紙撤回済み）
1. 商品マスタに不足の3項目（**販売価格・価格タイプ・販売タイプ**）を追加する
2. goods_csから定期的に更新する項目: 上記3項目＋**商品単価・子カテゴリ（コード）・ブランド品番**
3. **CS別品番は上書きしない**（多くのアプリがCS別品番で商品マスタを引いているため）
4. ZOZO上でCS品番が変わった商品は、**新しいCS品番でレコードを追加**する
5. **JANコードは古いレコードから新しいレコードへ移す**（JANは重複禁止のため、古い方を消してから入れる）
6. **古いレコードはアーカイブにする**。セール・フォローで同じ商品が2重に出力されるのはNG
   - 定期更新（価格など）は販売中のレコードだけに入れる（アーカイブのレコードは更新しない）
   - 古いレコードは削除しないので、変更前のCS品番で届く売上（精算書はView「CS品番」で引く）や過去の発注明細・旭川在庫のルックアップからは引き続き参照できる

7. **更新は、各業務担当者（セール・フォロー・精算）が業務の直前に行う**

## 確認済みの事実（kintone設定、2026-09-10）
- 商品マスタ: 396,560件・38項目。販売価格/価格タイプ/販売タイプに当たる項目は無い
- 重複禁止: CS別品番, JANコード → CS別品番をキーにしたCSV更新が可能（キーの値そのものは変更不可）
- 商品展開ID: 数値項目、空欄80件のみ。重複禁止ではない
- 子カテゴリの項目は「子カテゴリコード」（数値）。goods_csは子カテゴリ名のみ → ZOZO子カテゴリマスタで名前→コード変換が必要（9/1統合と同じ）

## 更新の流れ（案）
goods_cs全量DL → 前回分と商品展開IDで比較 → 変わった行を抽出 → 商品展開IDから商品マスタの現CS別品番（販売中のレコード）を引いてキーにする → CSV取込
CS品番が変わった行: ①古いレコードのJANを消す ②新しいCS品番でレコード追加（kintone側の項目は古いレコードからコピー、ZOZO由来の項目はgoods_csの値、JANを移す）③古いレコードをアーカイブ
（6日間の変化量の目安: 販売価格22,526 / 価格タイプ7,656 / 商品単価1,689 / ブランド品番170 / CS別品番17 / 子カテゴリ0）

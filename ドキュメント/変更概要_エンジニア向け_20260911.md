## ■1 背景

- goods_csの内容で商品マスタ（51）を更新すると、取込に毎回約4時間かかります（約40万件）
- 更新しないと、ZOZO側でCS品番・ブランド品番が変わった商品を引けなくなります（9/1→9/7の6日間で、同じ商品展開IDのままCS別品番が変わったもの17件、ブランド品番が変わったもの170件）
- 影響（コード上の動き）
  - 精算書（45）: 売上発送・特別処理のCS品番で商品マスタを引けないと、子カテゴリコードが取れず、子カテゴリマスタ（44）が引けない → メーカーコード・精算区分が空、掛率が既定の100、単価（下代）未計算 → **精算金額がずれる**
  - フォロー（62）・セール（33）: 商品マスタのCS品番で在庫・在庫分析を引いているため、古いCS品番だと在庫・販売数が付かない
  - 返却（86）・旭川在庫（69）: CS品番で商品マスタを引けず、メーカーID・メーカー名などが空になる

## ■2 変更の方針（案）

1. **goods_csアプリを新設**し、ZOZOの展開単位CSV（goods_cs.csv）をそのまま持たせます。キーは商品展開ID（CS品番が変わっても変わらない）
   - アプリの作成と取込の仕組みは、こちらで用意します（更新方式は検討中）
2. **商品マスタは登録時の値の置き場**とし、goods_csの内容では更新しません。書き込みは商品展開IDの空欄埋めだけにします
3. アプリどうしは書き換え合わず、突き合わせは読む側（JS）で行います
4. ZOZOで変わる値（CS品番・ブランド品番・カテゴリなど）はgoods_csアプリから読み、登録時の値（メーカー・元品番・カラー名称・メーカーサイズ・JANなど）は商品マスタから読みます

## ■3 改修をお願いしたい内容（案）

### 共通
- **CS品番の読み替え関数**を1つ用意していただきたいです
  - 今のCS品番 → goods_csアプリ → 商品展開ID → 商品マスタ（逆方向の、商品マスタのCS品番 → 今のCS品番も必要）
  - goods_csアプリは約40万件になるため、全件取得ではなく、必要なCS品番だけを分割取得する形でお願いします（セールJSの `fetchRecordsInChunks` が流用できそうです）

### アプリ別
| アプリ | 今の読み方 | 改修内容（案） |
|---|---|---|
| 精算書（45） | 売上発送・特別処理はCS品番、Goodsinfoはブランド品番で商品マスタを引く（3か所） | 金額計算は「今のCS品番 → goods_csアプリの親カテゴリ名＋子カテゴリ名 → 子カテゴリマスタ」で行う。メーカー名は子カテゴリマスタのメーカーコード → メーカーマスタ。**元品番だけ**商品展開ID経由で商品マスタから取る |
| フォロー（62） | 「販売中の商品」ビューで商品マスタを取得し、CS品番で在庫・在庫分析を引く | 取得直後にCS品番（とブランド品番）を今の値へ読み替える。差し戻し中の修正と同時に進められればと考えています |
| セール（33） | フォローと同じ。ブランド品番でまとめる処理あり | 取得直後の読み替え＋ブランド品番でのまとめ方 |
| 返却（86） | CS品番で商品マスタを引く | 見つからないCS品番を商品展開ID経由でたどる |
| 旭川在庫（69） | CS品番で商品マスタを引く（JS）＋ルックアップ | JS部分は返却と同じ。ルックアップ部分は別途相談させてください |

補足（こちらで確認した事実）:
- goods_csの「子カテゴリ」列は名前です。子カテゴリ名だけでは重複がありますが、「親カテゴリ名＋子カテゴリ名」は子カテゴリマスタ（1,010件）の中で重複がありません
- 9/7のgoods_csと突き合わせると、878組中875組（行数で99.8%）が子カテゴリマスタに見つかりました。未登録の3組（938行）の扱いはこちらで確認します
- 名前でたどった子カテゴリIDと、今の商品マスタの子カテゴリコードが一致するかは、こちらで確認中です

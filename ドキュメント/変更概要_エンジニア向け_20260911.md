## ■1 背景

- goods_csの内容で商品マスタ（51）を更新すると、取込に毎回約4時間かかります（約40万件）
- goods_csには更新日の列がありません（「販売開始日」はセール開始で書き換わり、終了しても戻らないため代わりになりません）。ファイル単体では変わった行が分からず、商品マスタをZOZOに合わせるには全件更新になります
- **前回分との比較による差分更新も検討しましたが、商品マスタへの差分更新は見送りました。**理由は次のとおりです
  1. CS別品番は商品マスタのキー（重複禁止）で、精算書・返却・発注明細・旭川在庫のルックアップなどが引いています。上書きすると、古いCS品番で届くデータやルックアップが引けなくなります
  2. 上書きしない場合、CS品番が変わった商品ごとに「新CS品番でレコード追加 → JANを移す（JANも重複禁止のため旧レコードから消してから）→ 旧レコードをアーカイブ」が必要で、手順が煩雑になり誤りが起きやすくなります
  3. 更新は複数の担当者（セール・フォロー・精算）が業務前に行うため、差分の基準となる「前回分のgoods_cs」の共通管理や、同時実行時の扱いも必要になります
- そのため、ZOZOの内容は商品マスタとは別のアプリに持たせ、商品マスタは書き換えない方針としました（■2）
- 更新しないと、ZOZO側でCS品番・ブランド品番が変わった商品を引けなくなります（9/1→9/7の6日間で、同じ商品展開IDのままCS別品番が変わったもの17件、ブランド品番が変わったもの170件）
- 影響（コード上の動き）
  - 精算書（45）: 売上発送・特別処理のCS品番で商品マスタを引けないと、子カテゴリコードが取れず、子カテゴリマスタ（44）が引けない → メーカーコード・精算区分が空、掛率が既定の100、単価（下代）未計算 → **精算金額がずれる**
  - フォロー（62）・セール（33）: 商品マスタのCS品番で在庫・在庫分析を引いているため、古いCS品番だと在庫・販売数が付かない
  - 返却（86）・旭川在庫（69）: CS品番で商品マスタを引けず、メーカーID・メーカー名などが空になる

## ■2 変更の方針（案）

1. **goods_csアプリを新設**し、ZOZOの展開単位CSV（goods_cs.csv）をそのまま持たせます。キーは商品展開ID（CS品番が変わっても変わらない）
   - アプリの作成と取込の仕組みは、こちらで用意します（更新方式は検討中）
2. **商品マスタは登録時の値の置き場**とし、goods_csの内容では更新しません。書き込みは商品展開IDの空欄埋めだけにします
3. アプリどうしは書き換え合わず、突き合わせは読む側（JS）で行います
4. ZOZOで変わる値（CS品番・ブランド品番・カテゴリなど）はgoods_csアプリから読み、登録時の値（メーカー・元品番・カラー名称・メーカーサイズ・JANなど）は商品マスタから読みます
5. **「販売中」の判定もgoods_csアプリで行います。**商品マスタの「販売状況」は、担当者によると不定期に手で更新しており、明確なルールがありません。そのため9/1の商品マスタ統合時と同じルール（`商品マスタ統合_仕様書.md` §6-3: goods_csにある→販売中、無い／Web表示=0が一定期間／子カテゴリが引けない→アーカイブ）で判定したいと考えています

## ■3 改修をお願いしたい内容（案）

### 共通
- **CS品番の読み替え関数**を1つ用意していただきたいです
  - 今のCS品番 → goods_csアプリ → 商品展開ID → 商品マスタ（逆方向の、商品マスタのCS品番 → 今のCS品番も必要）
  - goods_csアプリは約40万件になるため、全件取得ではなく、必要なCS品番だけを分割取得する形でお願いします（セールJSの `fetchRecordsInChunks` が流用できそうです）
- **「販売中」を判定する関数**（上記■2-5のルール）。フォロー・セール・旭川在庫の「販売中の商品」ビューの代わりに使います。goods_csにはメーカーIDが無いため、メーカー単位での絞り込み方をご相談させてください

### アプリ別
| アプリ | 今の読み方 | 改修内容（案） |
|---|---|---|
| 精算書（45） | 売上発送・特別処理はCS品番、Goodsinfoはブランド品番で商品マスタを引く（3か所） | **売上発送**: 自レコードの「親カテゴリ」「子カテゴリ」名 → 子カテゴリマスタで掛率・精算区分を取る（メーカーのまとめ〔171行目〕と同じ方法。goods_csアプリ・商品マスタとも不要）。**特別処理明細**: カテゴリ項目がないため、CS品番で商品マスタを引き、見つからない分は商品展開ID経由でたどる。**元品番**: 同じく商品展開ID経由で商品マスタから取る |
| フォロー（62） | 「販売中の商品」ビューで商品マスタを取得し、CS品番で在庫・在庫分析を引く | 取得直後にCS品番（とブランド品番）を今の値へ読み替える。差し戻し中の修正と同時に進められればと考えています |
| セール（33） | フォローと同じ。ブランド品番でまとめる処理あり | 取得直後の読み替え＋ブランド品番でのまとめ方 |
| 返却（86） | CS品番で商品マスタを引く | 見つからないCS品番を商品展開ID経由でたどる |
| 旭川在庫（69） | ルックアップ（CS品番）で商品マスタの値をコピー。JSでも商品マスタを取得しているが、値は使われていない（56〜57行目） | JSの取得は不要であれば外していただければ。ルックアップ部分は別途相談させてください |

補足（こちらで確認した事実）:
- 精算書の金額のもと（販売価格・プロパー価格・出荷数など）はすべて売上発送のレコードから取っており、商品マスタが関わるのは掛率・精算区分だけです
- 売上発送アプリ（32）の先頭3万件で、「親カテゴリ」＋「子カテゴリ」名が子カテゴリマスタに29,998件見つかりました（同アプリの「子カテゴリID」項目は空でした）
- goods_csの「子カテゴリ」列は名前です。子カテゴリ名だけでは重複がありますが、「親カテゴリ名＋子カテゴリ名」は子カテゴリマスタ（1,010件）の中で重複がありません
- 9/7のgoods_csと突き合わせると、878組中875組（行数で99.8%）が子カテゴリマスタに見つかりました。未登録の3組（938行）の扱いはこちらで確認します
- 名前でたどった子カテゴリIDと、今の商品マスタの子カテゴリコードが一致するかは、こちらで確認中です

## 1. 前提（ユーザー方針）
- kintoneは開発最終段階。最優先は旧システム（Win10で稼働）から抜け出すこと
- 商品マスタのCS別品番は上書きしない（多くのアプリがCS別品番で引いている）
- セール・フォローで同じ商品が2重に出力されるのはNG
- 「商品マスタにgoods_csから差分更新する案」は白紙撤回（煩雑で間違いが起きそう、更新時に問題がありそう）
- **B案（ZOZOで変わる値はgoods_csアプリから読む）でエンジニアに提案する**（2026-09-11）
- goods_csアプリの新設・取込の仕組みはエンジニアへの依頼に含めない。更新方法はユーザーと議論する

## 3. 商品展開ID（アプリ間をつなぐキー）
- ZOZOで一意、CS品番が変わっても変わらない（2時点比較で17件確認）
- 商品マスタの「商品展開ID」: 数値項目、396,560件中 空欄80件。重複禁止ではない
- Excelからのkintone登録時には確定していない（ZOZO登録後に決まる）
- 入力方法（案）: ZOZO登録後、登録日で絞った展開単位CSVを取り込み、CS別品番をキーに空欄を埋める。空欄を一覧にするビューで取りこぼしを確認
  - 未確認: 登録日で絞ったCSVの見出し → ユーザーが後で提供

## 4. goods_csアプリの更新方法（未決・ユーザーと議論）

## 5. kintoneのJSを読んで分かったこと（2026-09-11）
### 5-1. 全体
- 価格はほとんど商品マスタから取っていない。フォローは在庫アプリ、セールは「在庫分析 → 在庫 → 商品マスタ（商品単価）」の順で、商品マスタは最後の予備
- 商品マスタから取っているのは主に、メーカー・子カテゴリ・元品番・カラー名称・サイズ・JAN
- **B案で本当に直す必要があるのは、CS品番・ブランド品番のずれへの対応**
  - フォロー・セール: 商品マスタのCS品番で在庫・在庫分析を引く → 古いCS品番だと在庫が付かない
  - 精算書・返却・旭川在庫: ZOZOの今のCS品番で商品マスタを引く → 変わった商品が見つからない
  - 対応は「商品展開IDで今のCS品番に読み替える」共通関数1つ＋各所の呼び出し。500件ずつ分割取得する関数（`fetchRecordsInChunks`）がセールJSにある

### 5-2. 精算書（45）
- 流れ: CS品番 → 商品マスタの子カテゴリコード → 子カテゴリマスタ（44）→ メーカーコード・精算区分・精算掛率 → 単価（下代）・下代合計金額
- 商品マスタで引けないと、メーカーコード・精算区分が空、**掛率は既定の100**、単価（下代）が計算されない → **精算金額が狂う**（今の運用でもCS品番が変わった商品で起きる）
- 子カテゴリはZOZO由来の値（6日間の変化0）。goods_csの「子カテゴリ」列は名前（コードではない）
- 子カテゴリ名だけでは重複あり（41件が複数の親に属する）。**「親カテゴリ名＋子カテゴリ名」は子カテゴリマスタ（1,010件）で重複なし**
- goods_cs（9/7）との突き合わせ: 878組中875組、398,412行中397,474行（99.8%）が子カテゴリマスタに見つかる。未登録3組・938行（例: `GT SELECT / A.T,C in the attic homme`）
- **元品番**: メーカー固有の品番（メーカーから支給）。メーカーに送るリストで分析に使われる → 必須。kintoneだけにある値なので商品マスタを引く必要がある
- 精算書の分け方（案）

| 用途 | 取り方（B案） | 引けなかったときの影響 |
|---|---|---|
| 金額計算（メーカーコード・精算区分・掛率） | 今のCS品番 → goods_csアプリの親・子カテゴリ名 → 子カテゴリマスタ | 子カテゴリマスタ未登録の組み合わせだけ |
| メーカー名 | 子カテゴリマスタのメーカーコード → メーカーマスタ | 同上 |
| 元品番 | 今のCS品番 → goods_csアプリ → 商品展開ID → 商品マスタ | 元品番の列が空欄になるだけ |

- 未確認: 名前でたどった子カテゴリIDと、商品マスタの子カテゴリコードが一致するか（商品マスタの「CS別品番・子カテゴリコード」CSVで突き合わせる）

### 5-3. 「販売中の商品」ビュー（商品マスタ）
- 条件は `販売状況 in ("販売中") and 登録メーカーID = "2"`。フォロー・セール・旭川在庫が使う
- 「販売状況」はgoods_csに無い項目。**誰がどう更新しているか未確認**（B案でも商品マスタ側で最新に保つ必要がある）

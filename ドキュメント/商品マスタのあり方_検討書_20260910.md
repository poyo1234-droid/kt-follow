## 4. goods_csアプリの更新方法（未決・ユーザーと議論）
事実:
- 商品マスタ（38項目）への全件更新は毎回4時間（約40万行、約28件/秒）
- 自作削除ツールの実測 112件/秒（40万件で約1時間の計算）
- 6日間の変化: 販売価格22,526 / 価格タイプ7,656 / 商品単価1,689 / 商品名775 / ブランド品番170 / CS別品番17 / バーコード11 / 販売開始日194,248

| 方式 | 件数 | 時間 | 特徴 |
|---|---|---|---|
| 差分更新 | 数万件（販売開始日を除く） | 20分前後（比例計算の見込み・未測定） | 最速。前回分goods_csの管理が要る |
| 洗い替え | 削除40万＋追加40万 | 削除約1時間＋追加約24分＝**約1時間25分** | 単純。途中は中身が半端。**削除が律速** |
| 全件更新 | 40万件 | 4時間（実績） | － |

- ユーザー判断: 1回20分前後なら各業務の前に回せる。更新は各担当（セール・フォロー・精算）が行う
- **決定（09-12・ユーザー）: 本番goods_csからは「商品コメント」列を削除して取り込む。**
  非常に重く、業務で使わないため。列数は28→27。所要時間の測定も27列で行う
- 決定（09-12・ユーザー）: **重複禁止フィールドは設けない。**洗い替えならキーが不要で、
  ZOZO側CSVに重複・空欄が1件でもあると全行が入らなくなるリスクを避ける。
  後から設定を追加することは可能（既存データに重複があると設定できない）

## 5. kintoneのJSを読んで分かったこと（2026-09-11）
### 5-1. 全体
- 価格はほとんど商品マスタから取っていない。フォローは在庫アプリ、セールは「在庫分析 → 在庫 → 商品マスタ（商品単価）」の順で、商品マスタは最後の予備
- 商品マスタから取っているのは主に、メーカー・子カテゴリ・元品番・カラー名称・サイズ・JAN
- **B案で本当に直す必要があるのは、CS品番・ブランド品番のずれへの対応**
  - フォロー・セール: 商品マスタのCS品番で在庫・在庫分析を引く → 古いCS品番だと在庫が付かない
  - 精算書・返却・旭川在庫: ZOZOの今のCS品番で商品マスタを引く → 変わった商品が見つからない
  - 対応は「商品展開IDで今のCS品番に読み替える」共通関数1つ＋各所の呼び出し。500件ずつ分割取得する関数（`fetchRecordsInChunks`）がセールJSにある

### 5-2. 精算書（45）
- 流れ（現状）: CS品番 → 商品マスタの子カテゴリコード → 子カテゴリマスタ（44）→ メーカーコード・精算区分・精算掛率 → 単価（下代）・下代合計金額
- **金額のもと（販売価格・プロパー価格・出荷数・価格タイプ・合計金額）はすべて売上発送アプリ（32）のレコードから取る**（main.js 118〜131・180・543〜581行目）。商品マスタが関わるのは子カテゴリコード経由の掛率・精算区分（販売価格／元上代のどちらを使うか）だけ。特別処理明細（42）は合計金額・数量から計算し、掛率だけ子カテゴリ経由
- メーカーごとのまとめ（171行目）は、すでに売上発送の「親カテゴリ」名 → 子カテゴリマスタで行っている
- 売上発送アプリには「親カテゴリ」「子カテゴリ」（名前）がある。先頭3万件で「親＋子カテゴリ名」→ 子カテゴリマスタが29,998件一致。同アプリの「子カテゴリID」項目は3万件すべて空
- 特別処理明細アプリ（42）にはカテゴリの項目がない
- 商品マスタで引けないと、メーカーコード・精算区分が空、**掛率は既定の100**、単価（下代）が計算されない → **精算金額が狂う**（今の運用でもCS品番が変わった商品で起きる）
- 子カテゴリはZOZO由来の値（6日間の変化0）。goods_csの「子カテゴリ」列は名前（コードではない）
- 子カテゴリ名だけでは重複あり（41件が複数の親に属する）。**「親カテゴリ名＋子カテゴリ名」は子カテゴリマスタ（1,010件）で重複なし**
- goods_cs（9/7）との突き合わせ: 878組中875組、398,412行中397,474行（99.8%）が子カテゴリマスタに見つかる。未登録3組・938行（例: `GT SELECT / A.T,C in the attic homme`）
- **元品番**: メーカー固有の品番（メーカーから支給）。メーカーに送るリストで分析に使われる → 必須。kintoneだけにある値なので商品マスタを引く必要がある
- 精算書の分け方（案・09-11訂正。当初「金額計算はgoods_csアプリで行う」と書いたのは誤り）

| データ | 取り方 | goods_cs | 商品マスタ |
|---|---|---|---|
| 売上発送 | 自分のレコードの親・子カテゴリ名 → 子カテゴリマスタ | 不要 | 不要 |
| 特別処理明細 | カテゴリ項目がないため、CS品番から引く | 必要 | 必要 |
| 元品番 | CS品番 → 商品マスタ（見つからない分は商品展開ID経由） | 必要 | 必要 |

- 売上発送の分はgoods_csアプリなしで直せる（B案を待たずに先行できる）。引けなかったときの影響は、元品番なら列が空欄になるだけ

- 未確認: 名前でたどった子カテゴリIDと、商品マスタの子カテゴリコードが一致するか（商品マスタの「CS別品番・子カテゴリコード」CSVで突き合わせる）

### 5-2b. 商品マスタにしかない値と、商品マスタを見ないと動かない仕組み
- 商品マスタにしかない値: 登録メーカーID／メーカー名・元品番・カラー名称・メーカーサイズ・JANコード（kintone生成）・FUN担当者名（販売状況も商品マスタにしかないが、goods_csアプリから判定する方針にした）
- 他で代わりが取れる値: CS別品番・ブランド品番（goods_cs）、商品単価（goods_csのプロパー価格）、子カテゴリコード（親・子カテゴリ名 → 子カテゴリマスタ）、主性別（goods_csの性別）。商品名はgoods_csにもあるが「Access優先」との判断が要る。カラーコード・商品タイプコードはgoods_csの値と同じか未確認
- 商品マスタを見ないと動かない: フォロー・セール・精算書（元品番）・返却・発注・検品（VBA）・旭川在庫（ルックアップ）
- 見なくてよい: 発注明細（35）のルックアップ（ブランド品番だけ）。旭川在庫（69）のJSは商品マスタを取得しているが値を使っていない（56〜57行目）
- 結論: 商品マスタを見なくなる仕組みはほとんど無い。B案の要点は「商品マスタを変わらないキー（商品展開ID）で確実に引けるようにする」こと

### 5-2c. JAN納品書発行.xlsm（`納品書作成\export_VBA\Module_HattyuKintone.bas`、09-09エクスポート）
- 商品マスタをCS別品番で引く（納品書・JAN／撮影用CSV・CS品番チェック）。「納品書マスタ」というアプリはコードに出てこない
- 納品書: ブランド品番・商品名・カラー名称・メーカーサイズ・**商品単価 → G列「上代（税抜）」・H列「上代合計」**・JAN（1353〜1356行目）。**納品書に印刷されている（担当者回答 09-11）** → 登録時の単価のままでは不可。納品書VBAもB案の改修対象
- 初回納品はCS品番を初回納品アプリ（kintone登録時の値）から取るため、商品マスタとずれない
- ユーザー見解: 単価は登録時のままではまずい。ブランド品番・CS別品番はファンアライブ側で決めるので古くても問題ない。商品展開IDはZOZOのバックオフィス画面に出ていない可能性があり、手入力の検索キーにすると使いづらい
- 案: 入力はCS品番のまま。商品マスタに無いときだけgoods_csアプリで商品展開IDへ読み替えて引き直す。上代はgoods_csのプロパー価格から取る

### 5-3. 「販売中の商品」ビュー（商品マスタ）
- 条件は `販売状況 in ("販売中") and 登録メーカーID = "2"`。フォロー・セール・旭川在庫が使う
- 「販売状況」はgoods_csに無い項目。kintoneのJSには書き換える処理が無い。9/1統合では goods_cs から決めた（`260318ー登録エクセルkintone化\商品マスタ統合_仕様書.md` §6-3: §6-1／§6-2〔子カテゴリ引けず〕／§6-4〔Web表示=0 かつ 一定日以前〕→アーカイブ、goods_csにある→販売中、無い→アーカイブ）
- 担当者回答: その後は不定期・ルールなし・気づいた人が手で更新 → このままでは実態とずれていく
- **決定: B案では「販売中」をgoods_csアプリから同じルールで判定する。**商品マスタの販売状況は使わない。goods_csにはメーカーIDが無いため、メーカー単位の絞り込み方はエンジニアと相談
- 「登録メーカーID = 2」で絞り込まれたまま。本番前に外す予定か未確認

フォローリスト出力の修正依頼

お世話になっております。

キントーンで出力したフォローリストと旧システムの出力を、メーカーID=2（株式会社スタンレーインターナショナル様。旧1,145件／キントーン3,608件）で全項目突き合わせました。
その結果、修正をお願いしたい点が8件ありましたのでご連絡します。

対象: フォローリスト出力のカスタマイズJS（`260909-フォローmain.js.txt`）


■ 1. 出力対象の絞り込みを追加してください（Viewの新規作成が必要）

現在は商品マスタの「販売中の商品」ビューを全件出力していますが、旧システムはメーカー在庫切れの商品を出力していません。

メーカー2では、キントーン3,608件のうち旧システムに無い2,463件を調べたところ、全件がメーカー在庫切れSKUリストと一致しました（100%）。

商品マスタのフィールド「メーカー在庫状況＝在庫あり」で絞り込むViewを新規作成し、スクリプトの参照先をそのViewに変更してください。これで3,608件→1,145件となり、旧システムと行数が一致します。


■ 2. 販売タイプの「通常▲」ルールが未実装です

仕様書では「自動返却にマッチするCS品番がある製品のレコードの販売タイプは『通常▲』とする」となっていますが、現在のスクリプトは自動返却在庫のデータを読み込んでいません。

メーカー2で自動返却在庫リストと突き合わせたところ、該当243件が旧システムの「通常▲」243件と完全に一致しました（取りこぼし0・誤検出0）。現在はこの243件がすべて「通常」で出力されています。

自動返却在庫アプリを一括ロードし、CS別品番が存在する商品の販売タイプを「通常▲」に置き換える処理を追加してください。


■ 3. 該当データが無いときの既定値を 0 にしてください

現在は `|| ''` で空欄を出力していますが、旧システムは 0 を出力しています。

対象列: 在庫数量 / 販売可能数 / 直近7日販売数量 / 直近30日販売数量 / 最終入荷日からの経過日数 / お気に入り登録数


■ 4. 元上代にフォールバックを追加してください

現在は在庫アプリのみを参照していますが、ZOZOの在庫データには在庫のある商品しか含まれないため、在庫0の商品では空欄になります。メーカー2では1,145件中897件が該当しました。

「在庫 → 在庫分析 → 商品マスタ（商品単価）」の順に、最初に値があるものを採用する形にしてください。商品マスタまで見れば全件埋まることを確認済みです（カバー率: 在庫248件 → 在庫分析258件 → 商品マスタ1,145件）。

なお「販売価格」「価格タイプ」「販売タイプ」も同じ理由で空欄になりますが、商品マスタに該当フィールドが無いため、この3列を残すかどうかを弊社担当者に確認中です。方針が決まり次第あらためてご連絡します。


■ 5. JANコードを文字列として出力してください

キントーン出力のJANコードが、行1〜1000は文字列、行1001以降は数値になっています（メーカー2で文字列999件／数値2,609件）。

原因は、テンプレートのJANコード列（T列）に設定された「書式なしテキスト」が、シートの物理行数（1,000行）までしか効いていないことです。書き込みで自動拡張された行は General になり、`valueInputOption: 'USER_ENTERED'` で13桁の数字が数値に変換されています。エクスポートしたxlsxを確認したところ、行1000までが表示形式 `@`、行1001以降が `General` でした。

テンプレートの行数を増やす方法は、商品数の少ないメーカー様に大量の空行が出てしまうため避けたいです。スクリプト側で、JANコードを書き込む際に先頭にアポストロフィを付ける（`'1500000039844`）か、JANコードの列だけ `valueInputOption` を `RAW` にして書き込む形にしていただけますでしょうか。


■ 6. 在庫アプリに壊れたレコードが20件入っています（CSV分割ツールのバグ）

在庫アプリの件数が138,129件ですが、取込元CSV（`S20260907.csv`）は138,109行で、20件多くなっています。（在庫分析は147,211件で一致しています）

原因は `csv_splitter_gui.py` です。商品名に `"` を含む行がちょうど20件あり、それが分割時に2行に割れています。分割後のファイルは99,999行＋38,130行＝138,129行で、キントーンの件数と完全に一致します。

割れ方はマルチバイト文字の途中で切れており、「ス」（0x83 0x58）の1バイト目が失われて2行目が `X` で始まっています。`_force_quote_row` が「先頭が `"` なら既にクォート済み」とみなして素通しするため、`""スパン…T""` のような不正なクォートを補正できていないのが原因です。

該当商品:
　(Never) Acquiesce / JYP-JP658001（9件）
　(Never) Acquiesce / JYP-JP658002（7件）
　WINDS select / WIN-330483（4件）

バイト単位の処理をやめて `csv` モジュールで読み書きするなどの修正をお願いします。修正後に在庫アプリを再取込し、138,109件になることをご確認ください。


■ 7. 在庫・在庫分析の紐付けで正規化が抜けています

絞り込みでは

　`inv['CS品番']?.value?.trim()?.replace(/\r?\n/g, '')`

と正規化していますが、1件ずつ紐付ける `.find()` では

　`inventoryData.find(inv => inv['CS品番']?.value === csCode)`

と生の `.value` を厳密一致で比較しており、処理が非対称になっています。今回の不一致の主因ではありませんでしたが、取りこぼしの要因になり得るため、`.find()` 側にも同じ正規化を適用してください。


■ 8. salegoods のデッドコードについて

`allSaleGoodsData` を読み込み・絞り込みまでしていますが、出力に一切使われていません。salegoods はブランド単位のデータで今回の用途には使わない方針となりましたので、削除するか、別の用途を想定されているようでしたら教えてください。


■ 修正後の確認方法

メーカーID=2で再出力し、旧システムの

　`フォローリスト20260907\00002-株式会社 スタンレーインターナショナル様_フォローリスト20260907.xlsx`

とCS別品番をキーに突き合わせてください。行数が1,145件になり、JANコードが全件文字列型になっていれば想定どおりです。

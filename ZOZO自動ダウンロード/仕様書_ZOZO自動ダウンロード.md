# ZOZO BACK OFFICE goods_cs 自動ダウンロード 仕様書

ZOZO BACK OFFICE から展開単位CSV（`goods_cs.csv`・約970MB・約40万行）を
毎朝自動で取得する。今回の範囲は**ダウンロードまで**。kintone の削除・取込には繋げない。

- リポジトリ: `260907-フォローデータ`（origin: `poyo1234-droid/kt-follow`）
- 実行環境: 会社PC 1台（ログオン済み・電源ON）。Python 3.13.9 / Playwright 1.62.0 / Chromium 151
- 着手: 2026-09-13
- **改訂: 2026-09-14。1本で落とす方式は ZOZO 側のタイムアウトに当たるため、登録日で7分割して落とす方式に改めた（§1.7〜§2）**

---

## 1. 調べて分かったこと（実測・2026-09-13）

### 1.1 ログインは二段構え

| 段 | 方式 | 内容 |
|---|---|---|
| 1段目 | **HTTP Basic認証** | `https://to.zozo.jp/to/` が `WWW-Authenticate: Basic realm="to.zozo.jp"` を返す。Playwright の `http_credentials` で通す |
| 2段目 | ログインフォーム | `form action=/to/Default.asp` method=POST |

2段目のフォーム構成:

```
hidden  c = "Login"
hidden  csrf_token = "bo_sec_tkn_..."   毎回変わる（フォームから読んで送る必要がある）
hidden  TerminalID = ""                  空のまま送って通る
input   name='LoginName'  id='UserID'
input   name='Password'   (idなし)
button  type='submit'  text='ログイン'
```

セレクタは `#UserID` / `input[name='Password']` / `button[type='submit']`。

### 1.2 商品検索

メニューはドロップダウンで隠れていてクリックできないため、**URLを直接開く**。

| 画面 | URL |
|---|---|
| 商品検索 | `https://to.zozo.jp/to/GoodsSearch.asp?c=Init` |

検索実行は `form1` の `button[name='search'][value='SEARCH']`（hidden `c=Search`）。

**検索条件は既定のまま触らない。** 検索は1〜2秒で終わる。

| 項目 | 既定値 | 備考 |
|---|---|---|
| `Top`（対象） | `1` = 50件 | **CSVの中身には影響しない（実測で確認済み）**。画面表示の件数だけ |
| `SearchDb` | `1` = アクティブ商品 | もう一方は `2` = アーカイブ商品 |
| `StockType` / `SellType` / `ShowWebFlag` / `CustomerTypeID` / `ExternalStockType` | すべて「指定なし」 | |
| `OrderBy` | `1` = 販売順 | |

> `Top=0`（指定なし・全件）にしても結果は同じ。ラジオは装飾で隠れているため
> `check()` すると待ち続ける。設定する場合は JS で `e.checked = true` を入れる。

### 1.3 CSVのダウンロード

検索結果画面に3つのCSVリンクが現れる。

| リンク | URL |
|---|---|
| 商品単位CSV | `GoodsSearch.asp?c=ListDownLoadGoods` |
| **展開単位CSV** | **`GoodsSearch.asp?c=ListDownLoadCS`** ← goods_cs はこれ |
| 一括委託返却用CSV | `GoodsSearch.asp?c=TenantDeliveryCSV` |

応答ヘッダ:

```
HTTP 200
Content-Type: Application/vnd.ms-excel-csv
Content-Disposition: attachment; filename=goods_cs.csv
Transfer-Encoding: chunked
（Content-Length は返らない。生成しながら流している）
```

`Content-Length` が無いので**進捗率は出せない**。受信済みバイト数のみ表示できる。

**chunked なので、データの最後に「サイズ0の終端チャンク」が来る。** これがプロトコル上の
完了信号になる。途中で接続が切れた場合、Python の `http.client` は終端チャンクが
来ないことを検知して **`IncompleteRead` を投げる（`test_truncated.py` で検証済み）**。
このとき書きかけのファイルは残らない。

ただし、ZOZO側が途中までを正常なデータとして終端チャンクを送ってきた場合は
プロトコル上は正常完了に見える。これを捕まえるのが §3 の自前検査。

### 1.6 つまずいた点と対処

| 事象 | 原因 | 対処 |
|---|---|---|
| `401 権限がありません` | `settings.txt` の値をクォートで囲っていた | クォートは書かない（`=` の右側がそのまま値） |

### 1.7 2026-09-14 の失敗：ZOZO 側のスクリプトタイムアウト

初回の自動実行が **ASP 0113（Server.ScriptTimeout）** で打ち切られた。

受信したファイルの末尾に、CSV ではなく IIS のエラーページが書き込まれていた。

```
Active Server Pages エラー 'ASP 0113'
スクリプトがタイムアウトしました
/to/GoodsSearch.asp
スクリプトを実行する時間の制限を超えました。（Server.ScriptTimeout）
```

**通信が切れたのではない。**CSV を生成している ASP が時間切れで自ら停止し、
途中までのデータにエラー文を足して正常終了した。HTTP は 200、chunked の終端チャンクも
正常に来るため `IncompleteRead` は発生しない。§1.3 で想定していた
「ZOZO側が途中までを正常なデータとして終端チャンクを送ってきた場合」がこれにあたる。

| 項目 | 値 |
|---|---|
| HTTP 200 を受けた時刻 | 08:42:26 |
| 打ち切られた時刻 | 09:12:47（**1,821秒 ≒ 30分**） |
| 受信できた量 | 830.3 MB / 334,758行（前回は 970.3 MB / 399,786行） |

**ZOZO 側の `Server.ScriptTimeout` は 1,800秒と見られる**（サーバー設定は確認できないため推定）。

§3 の自前検査は3つとも作動し、入れ替えを中止して旧ファイルを守った。設計どおりに機能している。

**8:41 開始になった理由**: タスクは 8:00 だが `Interactive`（ログオン中のみ実行）＋
`StartWhenAvailable` で登録しているため、ログオンした時刻に実行された（§5）。

### 1.8 間に合わなかったのは転送速度が落ちたため

データ量はほぼ同じで、変わったのは速度だけだった。

| 実行日 | 開始 | 速度 | 結果 |
|---|---|---|---|
| 09-12 | 07:14 | 1.1 MB/s | 15分で完走 |
| 09-13 | 07:40 | 0.8 MB/s | 20分で完走 |
| 09-14 | 08:42 | 0.45 MB/s | **30分で打ち切り**（830MB地点） |

**NAS は原因ではない。**09-14 10:00 にローカルディスクへ受信して 0.46 MB/s だった（§1.9）。
ボトルネックは ZOZO 側の生成速度である。

**構造的な問題**: 970MB を 30分の枠で落とすには 0.54 MB/s 以上が要る。
09-13 の時点で所要20分、余裕は1.5倍しかなかった。速度はこちらで制御できず、
データは増える方向なので、1本で落とす方式はいずれ必ず破綻する。
**開始時刻を早めても構造は変わらない**（混雑を避けて速度を稼いでいるだけ）。

### 1.9 検索条件は CSV に反映される（2026-09-14 実測・`probe_split.py`）

**`c=ListDownLoadCS` は直前の検索条件を反映する。**これが分割方式の前提。

| 検証 | 条件 | 期待（9/12のファイルより算出） | 実測 |
|---|---|---|---|
| 1 | 商品コード = 98032453 | 10行 | **10行** / 0.02 MB |
| 2 | 登録日 2022/01/01〜01/31 | 3,180行・7MB前後 | **3,180行** / 7.11 MB |
| 3 | 登録日 2022/01/01〜12/31 | 47,057行・112MB前後 | **47,057行** / 110.90 MB / 242.6秒（0.46 MB/s） |

- **予測と実測の誤差は1%。**9/12 のファイルから全チャンクのサイズを予測してよい
- **`RegistDTFrom` / `RegistDTTo` は両端を含む**（検証2で To 指定日のデータが入った）
- **条件はサーバー側のセッションに保持される。**CSV の URL は
  `GoodsSearch.asp?c=ListDownLoadCS` だけでパラメータを持たない。
  検索フォームを送信 → 同じURLを GET、の順でしか絞れない
- したがって**並列ダウンロードはできない**。条件が1つしかないため、受信中に次の検索を
  投げると条件が壊れる。1本ずつ順に落とす
- **日付入力は JS で値を入れる。**`fill` のあと `Escape` を押すと日付ピッカーが値を戻す
  （実測で `RegistDTTo` が空になり0件になった）。`SEARCH_RegistDT` チェックボックスも
  CSSで隠れているため JS で `checked = true` にする

## 2. 採用する方式（2026-09-14 改訂）

**登録日で7分割し、1本ずつ順に落として最後に結合する。**
1リクエストあたりを ZOZO の30分制限の内側に収めるのが目的で、総時間は短くならない。

```
Playwright (Chromium, headless, UA=Chrome)
  ├─ Basic認証つきで https://to.zozo.jp/to/ を開く
  ├─ #UserID / Password を埋めてログイン          ← 1回だけ
  │
  ├─ チャンク1: GoodsSearch.asp?c=Init を開く
  │            SEARCH_RegistDT / RegistDTFrom / RegistDTTo を JS で入れて検索
  │              ↓ Cookie を取り出す
  │            Python urllib で c=ListDownLoadCS を GET し 1MBずつ書き出す
  │              ↓ チャンク検査（§3）
  ├─ チャンク2 …（同じことを7回）
  └─ ブラウザを閉じる
        ↓
  7本をヘッダ1つ・CP932のままバイト連結して goods_cs.csv を作る
        ↓
  結合後の検査（前回比）→ 通れば入れ替え
```

### チャンクの区切り（1本150MB以下）

| # | 登録日の範囲 | 行数 | 容量 | 0.46MB/s | 速度が半減しても |
|---|---|---|---|---|---|
| 1 | 〜2021/09/30 | 66,575 | 142.1 MB | 5.1分 | 10.3分 |
| 2 | 2021/10/01〜2022/12/31 | 60,171 | 144.0 MB | 5.2分 | 10.4分 |
| 3 | 2023/01/01〜2023/12/31 | 61,203 | 142.8 MB | 5.2分 | 10.4分 |
| 4 | 2024/01/01〜2024/12/31 | 57,835 | 137.2 MB | 5.0分 | 9.9分 |
| 5 | 2025/01/01〜2025/08/31 | 53,714 | 128.8 MB | 4.7分 | 9.3分 |
| 6 | 2025/09/01〜2026/02/28 | 50,097 | 131.4 MB | 4.8分 | 9.5分 |
| 7 | 2026/03/01〜**実行日** | 50,190 | 143.9 MB | 5.2分 | 10.4分 |
| | **合計** | **399,785** | **970 MB** | **約36分** | |

- 行数・容量は 9/12 のファイルからの算出値（誤差1%・§1.9）
- **今回の失敗は「速度が半分になったこと」が原因だったので、さらに半減しても
  最大10.4分で収まる設計にした。**30分に対して3倍の余裕がある
- 先頭チャンクの始端は最古（2017/09）より十分古い日付にする
- **最終チャンクの終端は実行日。**未来日は入れない（登録日が未来のレコードは無い）。
  終端を空にすると0件になるため、必ず日付を入れる
- 境界は `settings.txt` に持つ（§4）。前チャンクの終端の翌日を次の始端にすれば重複しない

### なぜ分割数を増やしても速くならないか

落とす総量は 970MB のままで、ボトルネックは ZOZO 側の生成速度。
**チャンク間で増える手間は検索の数秒だけ**（実測 0.5〜3.2秒）で、
7チャンクでも合計20秒ほど。全体36分に対して1%未満なので、
受信中に次の検索を投げる等の細工は割に合わず、条件が壊れる危険だけが残る。

別ログインで2セッション並列にすれば理屈上は可能だが、同じサーバーを取り合うだけで
倍速にはならず、**すでにタイムアウトを起こしている相手に負荷を倍かける**ことになる。
朝5〜6時台に終わればよい処理なので、総時間の短縮は追わない。

### ファイル受信の方式（2026-09-13 から変更なし）

ブラウザのダウンロード機構を使う方式（`probe_download.py`）でも成功はするが、
一時ファイルからNASへコピーし直すぶん余計にかかり、進捗も見えない。
**受信は Python で直接ストリーミングする。**

## 3. ダウンロード成否の判定

ZOZO画面に件数表示が無く、`Content-Length` も返らないため、
**「本来何バイト来るはずか」が事前に分からない**。通信が途中で切れても
プログラムからは「最後まで受け取った」ようにしか見えないので、自前で検査する。

**検査を通過してから初めて旧ファイルを OLD へ移す。**
通過しなければ旧ファイルはそのまま残し、受信したものは `.失敗_日時` の名前で残す。
壊れたデータが正になり、正しい前回分が OLD へ押し出されるのを防ぐため。

| # | 検査 | 捕まえるもの | 通らなかったら |
|---|---|---|---|
| 1 | ヘッダの列数が28か | ZOZO側の仕様変更（列の増減） | **中断** |
| 2 | 列名が §1.5 と一致するか | 表記ゆれ | **警告のみ・続行**（前例があるため） |
| 3 | ファイルが改行で終わっているか | 行の途中でのブツ切れ | **中断** |
| 3b | 最終行の引用符が閉じているか（`"` が偶数） | 引用符の途中でのブツ切れ | **中断** |
| 4 | 前回比で行数・サイズが **10%以上減っていないか** | 行の境目できれいに切れたケース | **中断**（増加は警告のみ） |

### 決めたこと（2026-09-13）

- **行数は改行基準**で数える。`商品コメント` の改行も数に入るため実レコード数とは
  ズレるが、前回との比較用途には十分で、1GBでも7秒で済む
- **閾値は -10%。減少方向だけを中断の対象にする。** ダウンロードが途中で切れたときに
  ファイルが増えることはあり得ず、欠損は必ず減る方向に出る。一方で商品の大量追加による
  増加は正常な動きなので、増加で止めると「正常なのに止まる日」を作るだけになる。
  増加が10%を超えた場合はログに残すだけで続行する
- 10%という幅は40万行に対して4万行。3%程度の欠損は素通りするが、通信が切れるときは
  大きく欠けることがほとんど（検証時に切れかけた例は全体の2.6%）。5%にすると
  セールや大量登録の時期に誤検知する恐れがある
- ~~**失敗はメッセージボックスで知らせる**~~ → **2026-09-14 改訂: 通知はログのみ**（§3「失敗したチャンクの再取得」）

### 列数をカンマで数えてはいけない

`商品コメント` 列にはHTMLが入っており、**引用符の中にカンマも改行も含まれる**。
実測では最終行のカンマが28個あり、単純に数えると29列に見えた（実際は正常な1レコード）。
そのため「最終行の列数」ではなく、**末尾が改行で終わっているか**と
**最終行の引用符が閉じているか**を見る方式にした。

### 完了判定は3層（2026-09-13 すべて検証済み）

| 層 | 何を見るか | 検証結果 |
|---|---|---|
| 1 | HTTPの終端チャンク | 途中で切れると `IncompleteRead`。書きかけのファイルは残らない |
| 2 | `Content-Type` が csv / excel か | HTMLが返ると `RuntimeError` で弾く |
| 3 | 自前の検査（下表） | 6ケースで確認 |

`test_truncated.py` を実行すれば1層目と2層目をいつでも再確認できる。

### 検査の動作確認（2026-09-13）

実データの先頭2MBから異常系のファイルを作り、6ケースすべてで期待どおりに動くことを確認済み。

| ケース | 結果 | 捕まえた検査 |
|---|---|---|
| 正常 | 通過 | — |
| 行の途中で切断 | 中断 | 末尾の改行 |
| 引用符が未閉鎖 | 中断 | 引用符の偶数 |
| ヘッダ列が不足 | 中断 | 列数 |
| 前回比 -50% | 中断 | サイズ・行数の減少 |
| 前回比 +50% | 通過（警告のみ） | — |

**「行の途中で切断」はサイズの減少がわずか -0.0%（40バイト欠けただけ）で、
前回比の検査では捕まらなかった。**末尾の改行チェックだけが捕まえている。
検査を多層にしておく意味はここにある。

### 検査の限界（承知のうえ）

この検査が見ているのは**「量」だけ**であり、比較しているのは
**ファイルサイズ（バイト数）と行数（改行の個数）という2つの数値のみ**。
1行ずつの突合はしていない。

- 捕まえられる: 通信が途中で切れた、空ファイル、極端に小さい
- 捕まえられない: 行数は同じだが中身の値がおかしい、全体の数%だけ欠けている

つまり「**ダウンロードが最後まで届いたか**」の検査であって、データの正しさの検査ではない。
データの妥当性は取り込み側で見る領分とする。

全行突合という手もあるが、1GB×2の読み込みで数分かかるうえ、商品は毎日入れ替わるので
「差分が何%なら異常か」を決められない。量の比較で十分と判断した。

---

### 分割方式での検査（2026-09-14 改訂）

検査は**チャンクごと**と**結合後**の2段になる。
**1本でも欠けたら結合も入れ替えもしない。**旧ファイルはそのまま残す。

**チャンクごと**

| # | 検査 | 捕まえるもの | 通らなかったら |
|---|---|---|---|
| C1 | 末尾に `ASP 0113` / `Active Server Pages` が無いか | **ZOZO側のスクリプトタイムアウト**（§1.7） | 再取得 |
| C2 | ファイルが改行で終わっているか | 行の途中でのブツ切れ | 再取得 |
| C3 | ヘッダの列数が28か | ZOZO側の仕様変更 | **中断** |
| C4 | 0件でないか | 条件の入力ミス（`RegistDTTo` が空だと0件・§1.9） | 再取得 |
| C5 | 登録日が指定範囲に収まっているか | 条件が効いていない／セッションの取り違え | **中断** |

C1 を最初に置く。行数を数えたり前回と比べたりする前に、原因まで特定してログに出せる。

**結合後**

従来どおりの検査（§3 の表）をそのまま適用する。前回比 -10% で中断。

**警告（中断はしない）**

- 最終チャンクが **120MB または 8万件**を超えたら、
  「`settings.txt` に境界を1行足してください」とログに出す。
  当年チャンクは毎日伸びるため、放置するといずれ上限に当たる

### 失敗したチャンクの再取得

- 失敗したチャンクだけを再取得する。**最大2回、30秒あけて**
- 再取得しても駄目なら異常終了。全チャンクが揃わない限り入れ替えない
- 通知はログのみ（出社前に実行し、ログを確認する運用）

### 結合

- **ヘッダ1つ・CP932のままバイト連結。**2本目以降は先頭行を捨てて後ろに繋ぐだけ
- デコードはしない（cp932 のまま bytes で扱う）
- 一時的に約2GBの空きが要る（チャンク7本 970MB ＋ 結合後 970MB）

### スコープ外

kintone 取込用の加工は**この仕組みの外**。従来どおり、結合後の `goods_cs.csv` から
**商品コメント列を落として（28列→27列）10万行ごとに4分割**する。
kintone の制約は「1行目は項目名・500列以内・10万件以内・100MB以内」。
商品コメントを落とせば容量は問題にならず、**行数で決まる**。

## 5. タスクスケジューラ（登録済み・2026-09-13）

| 項目 | 値 |
|---|---|
| タスク名 | `ZOZO_goods_cs_download` |
| 実行するもの | `ZOZO自動ダウンロード\zozo_download.bat` |
| スケジュール | 毎日 8:00 |
| 実行ユーザー | `poyo`（**Interactive = ログオン中のみ動く**。失敗時のメッセージボックスを見せるため） |

| 多重起動 | しない（前回が動いていたら新しい方を捨てる） |
| バッテリー条件 | 無効化済み（既定では電源がバッテリーだと動かないため） |

powershell -Command "Get-ScheduledTaskInfo -TaskName 'ZOZO_goods_cs_download' | Format-List"

`LastTaskResult` が `0` なら成功。`0` 以外なら `log\zozo_download_YYYYMMDD.log` を見る。

## 7. 注意

- **多要素認証（MFA）の導入予定がある。** BACK OFFICE のお知らせに
  「【管理画面】多要素認証（MFA）導入のご案内」（2026-09-02付）がある。
  必須化されるとこの自動化は作り直しになる。内容の確認が必要

  掛かると自動化は止まる
- ID/PW をコードやログに書かない。調査スクリプトは `type=password` の値を
  出力せず、文字数だけを表示する

  ログオン時刻まで実行されない（2026-09-14 は 8:41 開始になった）。
  混雑する時間帯にずれ込むと速度が落ちるため、朝は早めにログオンしておく
